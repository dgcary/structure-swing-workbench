# 系统架构

## 1. 设计目标

Structure Swing Workbench 是一个单用户、人工决策优先的交易工作台。

系统必须把“研究”“判断”“纪律审计”“执行记录”分离：

- 研究模块可以提供信息和候选；
- 用户保留主观图表判断；
- 审计引擎只检查已定义规则；
- 执行数据与计划数据严格分离。

## 2. 建议技术栈

### 后端

- Python
- FastAPI
- Pydantic
- SQLAlchemy + Alembic
- PostgreSQL

### 前端

- TypeScript
- React + Vite
- KLineChart

### 调度

第一版优先使用轻量调度方式，不引入重型分布式任务系统。需要复杂任务队列后再扩展。

### 部署

- Ubuntu
- Docker / Docker Compose
- 单机部署优先

## 4. 核心架构约束

### 4.1 审计引擎必须可纯函数测试

输入标准化的：

- 交易计划；
- 计划版本；
- 动作；
- 账户快照；
- 持仓快照；
- 行情快照；

输出标准化审计结果。

审计引擎不得直接请求行情、数据库、LLM 或券商接口。

### 4.2 适配器隔离外部数据源

外部数据统一通过适配器转换成内部模型：

- 行情适配器；
- 账户适配器；
- 研究适配器；
- 未来券商适配器。

核心业务代码不得直接依赖 AKShare、某券商 CSV 格式或 TradingAgents 内部数据结构。

### 4.3 计划与成交分离

计划数据代表“准备做什么”，成交数据代表“实际发生了什么”。

不可用实际成交反向修改原计划历史。修改计划必须生成新版本。

### 4.4 用户主观判断不可被程序暗中替代

程序可以读取客观数据，但不能自行输出：

- 趋势向上 / 向下；
- Setup 自动成立；
- 支撑有效；
- 反转确认；
- 应该买入 / 卖出。

这些字段只能来自用户明确输入，或作为 AI 研究参考而不能直接进入纪律审计事实层。

## 5. 第一版数据流

```text
行情源 ───────┐
账户/CSV ─────┼──> 标准数据模型
研究系统 ─────┘          │
                          ▼
用户建立交易计划 ──> 纪律审计
                          │
                    审计结果/覆盖
                          │
                    手工执行交易
                          │
                    导入真实成交
                          │
                    持仓/成本/T仓
                          │
                        复盘
```

## 6. 开源复用原则

通用能力优先复用，差异化规则自研。

优先复用：

- FastAPI：API 框架；
- PostgreSQL：持久化；
- Alembic：数据库迁移；
- AKShare：第一版 A 股行情适配；
- KLineChart：K 线展示；
- TradingAgents / StockResearchPack：研究系统。

不直接把 vn.py 作为主框架；未来如果接券商或交易网关，可作为适配层候选。
